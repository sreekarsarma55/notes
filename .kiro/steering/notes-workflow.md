# Notes repo — working conventions

Read this before making any change to this repository.

## Branch strategy: one branch per subject

`main` is **only** the repo guide and the subject index. It must not accumulate subject content.

Each subject has its own long-lived branch:

| Subject | Branch |
|---------|--------|
| Machine Learning Techniques | `mlt` |

New subjects get a new long-lived branch (`dsa`, `stats`, `dbms`, ...).

### Where topic/week work goes

```text
                    ┌── mlt-week9 ──┐
subject branch  mlt ┤               ├──► PR base = mlt      ✅ correct
                    └── mlt-week10 ─┘

                                       ──► PR base = main   ❌ WRONG
```

1. Branch off the **subject branch**, not `main`:
   `git checkout mlt && git pull origin mlt && git checkout -b mlt-week9`
2. Open the PR with **`base` = the subject branch**:
   `gh api repos/{owner}/notes/pulls -f base="mlt" -f head="mlt-week9" ...`
3. Never target `main` for subject content. `main` only changes for repo-level
   things (this file, the root README, `.gitignore`).
4. Never push directly to `main` — always via a PR.

> `main` is kept deliberately small — currently just `README.md`, `.gitignore`
> and this steering file. If you ever find subject folders on `main`, that is a
> mistake to fix, not a pattern to follow.

## Layout inside a subject branch

```text
<subject>/
├── README.md          # subject index + how to use the notes
├── NN-topic.md        # one file per topic/week
├── cheat-sheet.md     # condensed formula recall
├── mock-solutions.md  # worked solutions to mocks/PYQs
└── images/
    ├── make_figures.py   # ALL figures are generated by this one script
    └── *.png
```

When adding a topic file, also update in the same PR:
- the subject `README.md` index table and big-picture diagram
- `cheat-sheet.md` with a new section for that topic

## Writing conventions

- Markdown with **plain-text math in ` ```text ` fences** — renders everywhere
  including GitHub and mobile. Do not use LaTeX `$...$` in prose.
- Use Unicode math symbols to match the existing files: `μ λ σ π θ φ Σ α β ε`,
  `‖·‖²`, `⁻¹`, `≤ ≥ ≠ → ⇒ ⇔ ∝ ∈ ⟂ ×`, subscripts `₀₁₂ⱼₖᵢ`, superscripts `²³ᵈ`.
  Write transpose as `^T`.
- Every topic file follows the same shape:
  *intuition → formulas/derivation → worked example → common exam traps table*.
- Cross-reference other weeks explicitly (e.g. "the kernel trick from Week 2")
  — the connections between weeks are the most examinable material.

## Figures

- Only add a figure if it teaches something a sentence cannot. No decoration.
- Add a new `fig_*()` function to `images/make_figures.py` and call it from
  `__main__`. Never commit a hand-made or one-off image.
- Setup each session (the sandbox is fresh, and `python` is not on PATH):
  ```bash
  python3 -m pip install matplotlib numpy
  python3 images/make_figures.py
  ```
- **Always run the FULL script before committing**, not individual functions.
  The module-level `rng` is shared, so calling one function alone produces a
  different random draw and silently rewrites unrelated committed PNGs.
- **Look at every figure you generate** with the image reader before committing.
  Several figures have shipped-then-been-caught as misleading (an ill-conditioned
  gradient-descent path that appeared to stall; a curse-of-dimensionality plot
  whose outlier flattened the trend). A figure that renders is not a figure that
  is correct.

## Accuracy bar

Before opening a PR:

1. **Numerically verify every formula and worked example.** Write a throwaway
   script (e.g. `/tmp/verify_weekN.py`), assert each claimed number, and prefer
   checks that could actually fail — exhaustive enumeration, Monte-Carlo,
   random-model sweeps, perturbation tests for "is this a minimiser", affinity
   tests for "is this linear".
2. If an assertion fails, work out whether the **notes** or the **test** is
   wrong. Both happen. Say which in the PR description.
3. Check that every image path and cross-file link resolves.
4. Review `git diff --cached --stat` for unintended changes (stray `__pycache__`,
   accidentally regenerated figures).

State in the PR description what was verified and what was left unverified.
Never describe a claim as checked when it was only restated.
